# ChainWatch 포트폴리오 원고

제출용 프로젝트 설명과 발표 대본. 구현·검증 기준은 [서비스 정의 12~13절](SERVICE_DEFINITION_V3.md), 실행 방법은 [README](../README.md)다. 현재 채용 여부와 지원 자격을 검증한 문서는 아니다.

## 포트폴리오 삽입용 본문

### ChainWatch — 검증인 관측·보상 대사 서비스

**Java 21 · Spring Boot · PostgreSQL · React · Geth · Teku**

테스트 블록체인의 검증인 잔액 변화가 보상·패널티·출금으로 설명되는지 확인하고, 판단에 사용한 원본 응답과 실패 이력을 보존하는 운영 서비스입니다. 로컬 개발망에서 실제 execution·consensus 클라이언트를 연동했습니다.

**문제**

검증인 잔액 차이를 그대로 보상으로 집계하면 패널티나 출금을 잘못 해석할 수 있습니다. 또한 서로 다른 체인 시점의 자료를 비교하거나 노드 응답 누락을 0으로 처리하면 근거가 부족한 결과를 정상으로 표시할 수 있습니다.

**설계와 구현**

- 확정 checkpoint와 state root에 조회 기준을 고정하고, Beacon execution payload를 Geth 블록과 대조하여 두 계층의 연결을 확인했습니다.
- 잔액 반영 구간과 증명 참여 epoch를 구분했습니다. 기초 잔액에 보상·패널티·출금을 반영한 계산값과 기말 잔액을 정수 gwei로 비교합니다.
- 차액 0은 MATCHED, 설명되지 않는 차액은 MISMATCH, 미확정·누락·미지원 흐름은 INCOMPLETE로 구분했습니다. 지원하지 않는 예치나 슬래싱을 보상 차액으로 흡수하지 않습니다.
- 외부 RPC 호출 전에 RUNNING 시도를 저장하고, 완료 여부와 수집한 원본을 보존했습니다. 같은 구간을 재실행해도 이전 실패 이력을 덮어쓰지 않습니다.

**검증 결과**

Geth·Teku 로컬 개발망에서 확정 slot의 16 → 24 진행을 확인했습니다. epoch 1 대사 중 Teku 프로세스를 일시 정지하여 약 5초 후 UPSTREAM_TIMEOUT / INCOMPLETE가 기록되는 것을 확인했습니다. 프로세스 재개 후 같은 epoch를 재실행한 보고서는 장애 전과 같았고, 검증인 3명의 미설명 차액은 모두 0 gwei였습니다. 정상·실패·복구 시도는 각각 별도로 보존됐습니다.

[실제 실험 기록](evidence/staking-v1-outage.json): #11 MATCHED → #12 INCOMPLETE → #13 MATCHED. 이 시간은 단일 실험값이며 처리량이나 성능 개선 수치가 아닙니다.

**적용 범위와 한계**

로컬 minimal 개발망의 Electra/Fulu를 대상으로 한 관측 자료 대사입니다. 합의 상태 전이·서명을 독립적으로 검증하지 않으며 MATCHED는 지급 승인이 아닙니다. 고객별 원장·자금 지급·공개망 장기 운영·프로세스 재시작 후 작업 자동 복구는 포함하지 않습니다.

## 경력기술서에 넣을 짧은 버전

**ChainWatch | 검증인 관측·보상 대사 개인 프로젝트**

- Java/Spring 기반으로 Geth·Teku를 연동하고, 확정 state root 및 execution 블록 연결에 근거한 epoch별 잔액 대사 구현.
- 보상·패널티·출금을 정수 gwei로 분리하고, 차액 불일치와 자료 부족을 별도 상태로 관리하여 근거 없는 정상 판정 방지.
- 로컬 노드 무응답 실험에서 timeout 보류 및 실패 이력 보존 확인. 재개 후 동일 구간 대사 결과 일치, 검증인 3명의 미설명 차액 0 gwei 검증.

기간과 본인 역할은 실제 기록을 확인하여 추가한다. 기존 회사 경력·운영 규모·개인 기여율은 이 문서에서 추정하지 않는다. AI 도움을 받은 코드도 면접에서 직접 설명하고 재현할 수 있는 범위로 제출한다.

## 직무에 연결해서 설명할 지점

| 프로젝트 근거 | 스테이킹 백엔드 관점의 설명 |
|---|---|
| 실제 Geth·Teku 개발망 연동 | HTTP API 구현을 넘어 체인 확정 시점과 외부 시스템 상태를 고려 |
| epoch 경계와 정수 금액 대사 | 보상 도메인을 잔액 변화·시점·누락 문제로 구체화 |
| INCOMPLETE와 원본 보존 | 불확실한 상태를 숨기지 않고 조사 가능한 운영 이력 제공 |
| pause/timeout/재실행 재현 | 통제된 장애에서 실제 동작을 검증하고 검증 범위를 명시 |

첨부했던 공고의 업무와 연결하는 설명이며 채용 적합성을 보장하지 않는다. Research 직무의 핵심 소스 분석·프로토콜 보안 검증 경험을 이 프로젝트만으로 충족했다고 표현하지 않는다.

### 녹화 전 확인

1. README대로 백엔드·프론트·개발망을 실행한다. 관리자 작업 시 로컬 개발 계정으로 로그인한다.
2. 현재 network의 MATCHED와 INCOMPLETE 이력이 있는지 확인한다. 없으면 README의 재현 스크립트를 실행한다. 단순 미래 epoch 보류를 노드 장애처럼 설명하지 않는다.
3. 실패·복구 이력의 ID를 메모하고 원본 근거 버튼이 동작하는지 확인한다.
4. 화면에는 앱과 필요한 터미널만 노출한다. 개발망 생성 로그의 테스트 키와 개인 브라우저 정보는 녹화하지 않는다.
5. 장애 실험은 미리 실행해 결과를 보여줘도 된다. 이때 “기록된 실험”이라고 설명하고 실시간 실험처럼 편집하지 않는다.

## 예상 질문과 답변 요지

**실사용자 없이 무엇을 검증했나요?**

실제 클라이언트 연동, 확정 시점, 잔액 대사, 응답 누락과 timeout, 이력 영속성을 검증했습니다. 실사용 트래픽·사용성·장기 운영 안정성을 검증한 것은 아닙니다.

**왜 모든 오류를 MISMATCH로 처리하지 않았나요?**

자료를 충분히 모았는데 계산이 맞지 않는 경우와, 자료가 없어서 계산 자체를 신뢰할 수 없는 경우는 운영자가 취할 조치가 다릅니다. 후자는 INCOMPLETE로 구분합니다.

**재실행이 멱등하다는 뜻인가요?**

같은 확정 구간의 보고서가 동일함을 확인했습니다. 실행 시도는 새로 저장됩니다. 지급이나 원장 쓰기가 없으므로 금융 거래의 exactly-once 처리를 구현했다고 말하지 않습니다.

**블록체인 검증기를 직접 구현했나요?**

아닙니다. 노드가 제공하는 상태·보상·블록을 연결하고 대사했습니다. 노드의 잘못된 응답 전체를 독립적으로 탐지하는 합의 검증기는 아닙니다.

**공개망으로 확장하려면 무엇이 달라져야 하나요?**

현재 full state 수집의 용량 제약을 바꾸고, 네트워크별 지원 범위·예치/종료 흐름·RPC 보존 정책을 검증해야 합니다. 분산 실행 잠금, 중단된 RUNNING 복구, 인증과 배포 설정도 별도 작업입니다.
